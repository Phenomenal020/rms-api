EXECUTIVE SUMMARY
--------------------------------------------------------------------------------
The subjects module is a focused org-admin CRUD surface for the permanent
school-level subject catalogue. It follows NestJS + Drizzle patterns used by
classes and term: OrgAdminGuard, global ValidationPipe, requireOrganizationId,
runWithDbContext for Postgres error mapping, ok() envelope, LoggingInterceptor.

Current surface: GET list, POST create, PUT update, DELETE remove — all org-scoped.
Ownership on write/delete is enforced via WHERE id AND organizationId (cross-org →
404). Duplicate names are blocked case-insensitively via uniqueIndex on
(organizationId, lower(name)). DELETE is blocked by subject_class_assignment
ON DELETE RESTRICT (23503 → clear 400). GET normalises null department → 'none'.

Prior gaps closed (2026-08-15): response envelope, GET org scoping, @IsIn /
@MaxLength, runWithDbContext on GET, LoggingInterceptor, DELETE endpoint,
case-insensitive unique name, department null mapping on read.


1) MIDDLEWARE — How can it be used here? Is it being used correctly?
--------------------------------------------------------------------------------

Current state
  • Global transport middleware in AppModule.configure(): requestId, requestLogger
    on all routes (except GET /health). ✅
  • main.ts: helmet(), express.json({ limit: '100kb' }). ✅
  • SubjectsModule has no module-level middleware — correct for this route. ✅

How middleware applies to /api/v1/subjects
  Middleware runs before guards, pipes, and the controller. It is the right
  layer for cross-cutting transport concerns that do not need DI:

  A) Request ID + logging (already wired app-wide) ✅
  B) Body size guard (already wired) ✅
  C) Rate limiting (optional, route-scoped) 📌
     Consider mutation rate limiter for POST / PUT / DELETE like classes.
  D) Request logging latency (app-wide requestLogger) ✅

What NOT to put in middleware for this route
  • Org resolution — service (requireOrganizationId) or DI guard.
  • Department enum validation — DTO / ValidationPipe.
  • Auth — global AuthGuard + OrgAdminGuard.

Verdict: Middleware is used correctly at the app level. Subjects needs no
module-specific middleware unless you add mutation rate limits.


2) EXCEPTION FILTERS — General use and improvements for this route
--------------------------------------------------------------------------------

How they work in NestJS (and in this project)
  • AllExceptionsFilter is registered globally in main.ts.
  • Service work wraps in runWithDbContext('subject', ...) which maps PG codes
    before they reach the filter.

Subjects-specific usage
  • getSubjects, createSubject, updateSubject, deleteSubject all use
    runWithDbContext('subject', ...). ✅
  • NotFoundException on PUT/DELETE when no row matches id + org.
  • requireOrganizationId throws UnauthorizedException / ForbiddenException
    before mutations run.

Mapped errors relevant to subjects
  • 23505 + context 'subject' → 409 Conflict
    "A subject with this name already exists in your school"
    (constraint: subject_organizationId_name_ci_key — case-insensitive)
  • 23503 + context 'subject' → 400 BadRequest
    "Cannot delete this subject because it is assigned to one or more classes.
     Remove class assignments first." ✅

Improvements status
  A) Wrap getSubjects in runWithDbContext ✅
  B) Response envelope success: true via ok() ✅
  C) postgres-error.mapper subject 23503 for DELETE ✅
  D) SubjectsExceptionFilter — not needed; global filter + mapper sufficient ✅

subject table
  • PK: text UUID default gen_random_uuid() — OK.
  • FK organizationId → organization ON DELETE RESTRICT — OK.
  • UNIQUE case-insensitive:
      uniqueIndex("subject_organizationId_name_ci_key").on(
        organizationId, sql`lower(name)`
      )
    Matches client duplicate check and classes CI pattern. ✅
    Apply with: pnpm drizzle-kit push
    If push fails, resolve existing case-variant duplicates first.
  • INDEX (organizationId) — OK.
  • department varchar(128) nullable — OK.
  • updatedAt $onUpdate — OK.

subjectClassAssignment
  • FK subjectId ON DELETE RESTRICT — DELETE subject blocked while assigned ✅
  • UNIQUE (organisationClassId, subjectId, academicTermId) — OK.

Cascade summary
  • INSERT/UPDATE — no cascades.
  • DELETE subject — BLOCKED if assignments exist (23503).
  • DELETE organization — BLOCKED by RESTRICT chain.

Optional hardening 📌
  • CHECK length(trim(name)) > 0
  • CHECK department IS NULL OR IN (...enum...)
  • Soft-delete / archival flag if schools need to hide subjects from pickers
