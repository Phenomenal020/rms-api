EXECUTIVE SUMMARY
--------------------------------------------------------------------------------
The student-view module is the form-teacher workspace: list classes (GET classes),
load a full class report grid (GET class-record), upsert per-student assessment
scores (POST save-scores), and submit a class-record export snapshot for admin
review (POST export). Reads use OrgMemberGuard (teachers + org admins); mutations
use UserGuard (form teachers only). Service methods return { success: true, data }
and enforce org/term scoping via requireTermInOrganization, form-teacher checks,
enrollment validation, and requireActive on writes.

Main gaps: (1) no runWithDbContext on any DB path; (2) no LoggingInterceptor;
(3) score DTO uses @IsNumber not @IsInt; (4) no @ArrayMaxSize on nested arrays;
(5) no duplicate subjectId detection in save payload; (6) N+1 queries inside
saveStudentScores transaction; (7) export pending-request check is app-only (race);
(8) getClassRecord returns 404 for non–form-teacher (403 semantics); (9) todo.md
is stale (DTO decorators exist). DB design for assessment → assessment_score
upsert via onConflictDoUpdate is sound; class_record_export snapshot stores JSON.

2) EXCEPTION FILTERS — General use and improvements
--------------------------------------------------------------------------------

Current usage
  • All service methods call Drizzle directly — no runWithDbContext wrapper.
  • Business rules → BadRequestException, NotFoundException, ForbiddenException.
  • saveStudentScores uses db.transaction; saveClassRecordExport nests
    getClassRecord then inserts request + record in a second transaction.

Mapped errors
  • assessment_score unique (assessmentId, assessmentStructureId) handled by
    onConflictDoUpdate — no 23505 surface. ✅
  • assessment_score CHECK score 0–100 — DB backstop if DTO allows float. ✅
  • No dedicated PgErrorContext for student-view / assessment_score in mapper.

Improvements
  A) runWithDbContext on all four service methods (reads + writes).
     FIX: wrap getTeacherClasses, getClassRecord, saveStudentScores,
     saveClassRecordExport in runWithDbContext('student', ...). ✅
  B) Map 23503 on assessment_structure delete elsewhere; score upsert path OK. ✅
  C) Export insert: unique pending per class/term not enforced in DB — see §8.
     FIX: partial unique index class_record_export_request_pending_class_term_unique
     on (classId, academicTermId) WHERE status = 'PENDING'; mapped 23505 in
     postgres-error.mapper student context. ✅

4) GUARDS — General use and current / improved usage
--------------------------------------------------------------------------------

  • GET classes, GET class-record → OrgMemberGuard (ROLE_USER | ROLE_ORG_ADMIN). ✅
  • POST save-scores, POST export → UserGuard (ROLE_USER only). ✅
  • requireTermInOrganization on all paths — org + term scoping. ✅
  • save-scores / export use requireActive: true — inactive/archived term blocked. ✅
  • assertFormTeacherForClass on save-scores — only form teacher of student's class. ✅
  • getClassRecord filters organisationClass.formTeacherId = userId — defence in depth. ✅
  • Org admin can read class record (OrgMemberGuard) but cannot POST (UserGuard). ✅

  A) TermStatusGuard (medium) 📌 — explicit ARCHIVED block on mutations (partially
     covered by requireActive today).
  B) getClassRecord unauthorized → NotFoundException; consider ForbiddenException
     for valid classId but wrong teacher (clearer 403 for client). 📌
  C) No guard on classId org membership beyond form-teacher join — sufficient. ✅

7) CODE QUALITY
--------------------------------------------------------------------------------

Strengths
  • getClassRecord builds a consistent grid: assignments × students × enrollments
    × assessment scores — matches client ResultTable model. ✅
  • saveStudentScores validates structure ids, assignment, enrollment before write. ✅
  • onConflictDoUpdate on assessment_score — idempotent upsert per component. ✅
  • saveClassRecordExport reuses getClassRecord for snapshot — single source of truth. ✅
  • Pending duplicate export rejected with clear BadRequestException. ✅
  • Comments mark validation phases ("Validate user supplied parameters"). ✅

Issues

  A) N+1 in saveStudentScores (medium) — per subject: select assignment, enrollment,
     assessment, then per score upsert. Large classes → many round-trips in one tx. 📌
  B) No duplicate subjectId check in studentSubjects array (medium). 📌
  C) saveClassRecordExport calls getClassRecord outside export tx — snapshot could
     drift if scores change between read and insert (acceptable for export workflow). 📌
  D) getClassRecord uses nested Drizzle with: — efficient for moderate class sizes;
     watch memory for very large enrollments. 📌
  E) requireOrganizationId imported in service file but unused — lint cleanup. 📌

10) DB DESIGN ISSUES
--------------------------------------------------------------------------------
  • Scores hang off assessment → studentSubjectEnrollment — correct enrollment
    scoping; one assessment per enrollment (unique). ✅
  • assessment_score CASCADE on assessment delete; structure RESTRICT — aligns
    with assessment-structure module. ✅
  • Full class record is computed, not stored — export snapshot in
    class_record_export_record.content (jsonb). ✅
  • class_record_export_request: no UNIQUE (classId, academicTermId) WHERE
    status = PENDING — duplicate pending possible under concurrency. 📌
  • student.classId SET NULL on class delete — save-scores rejects unassigned student. ✅


11) DB / SCHEMA OPTIMISATION
--------------------------------------------------------------------------------

assessment_score
  • UNIQUE (assessmentId, assessmentStructureId) — matches upsert target. ✅
  • CHECK score 0–100. ✅
  • INDEX on assessmentId, assessmentStructureId. ✅

class_record_export_request
  • INDEX organizationId, academicTermId, classId, status. ✅
  • Optional partial unique index on (classId, academicTermId) WHERE status = 'PENDING'. 📌

class_record_export_record
  • 1:1 requestId unique — one snapshot per request. ✅
  • content jsonb — no schema validation at DB layer. 📌

Cascade summary
  • Delete enrollment → RESTRICT if assessment exists (scores must be cleared first).
  • Delete term → RESTRICT on enrollments/assignments — expected.

Optional
  • Return assessmentStructureId sorted by displayOrder in class-record (client
    sorts today). 📌
  • Embed gradingSystem + assessmentStructure in class-record response to cut
    round-trips (API design). 📌
