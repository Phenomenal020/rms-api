EXECUTIVE SUMMARY
--------------------------------------------------------------------------------
The subject-view module exposes a single mutation: POST save-scores — bulk upsert
of assessment scores for many students in one subject (inverse pivot of
student-view save-scores). The controller applies UserGuard at class level.
The service is a **stub**: it throws InternalServerErrorException with a
"not yet migrated" message. DTOs (SaveSubjectScoresDto, StudentDataDto, ScoreDto)
are defined with class-validator decorators. There are **no GET endpoints**;
the client reuses student-view GET classes + class-record for the read pipeline.

Main gaps: (1) P0 — implement saveSubjectScores (port from student-view); (2) no
classId in payload — ambiguous when same subject exists in multiple classes;
(3) no subject-teacher column in schema — product assumes form teacher today;
(4) no runWithDbContext / LoggingInterceptor; (5) @IsNumber not @IsInt on score;
(6) no @ArrayMaxSize; (7) todo.md references old commented validation — stale;
(8) 500 stub should be 501 Not Implemented until ready. Read path dependency
on student-view is intentional for form-teacher subject pivot UI.

Open question (left as is): How would you account for score banks for
teachers who are not form teachers?

N+1 on saveSubjectScores (logged, not batched yet)
  saveSubjectScores is one db.transaction (atomic — correct). Inside it still
  walks payload.studentsData one student at a time and round-trips per row:
    SELECT student → (once per class) form-teacher check → SELECT assignment
    → SELECT enrollment → SELECT assessment (INSERT if missing)
    → per score column INSERT ... ON CONFLICT UPDATE assessment_score.
  Latency scales with roster size, not correctness. ~40 students × 3 scores is
  on the order of 160+ queries. Later: IN (...) loads + bulk insert assessments
  + bulk upsert scores. Defer until table edit is wired.
