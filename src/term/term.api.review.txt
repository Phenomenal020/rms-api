EXECUTIVE SUMMARY
--------------------------------------------------------------------------------
The term module manages org-scoped academic terms (create, list, patch dates/status).
It uses OrgAdminGuard, DTO validation with ISO date checks, cross-field date
validation in term-validation.ts, runWithDbContext on mutations, and application-
level “single ACTIVE term” demotion on PATCH. Strengths include immutable
academicYear/term identity, DB unique constraints aligned with business rules,
and status workflow comments in schema.

Main gaps: (1) createTerm calls requireOwnerOrganizationId(member.role === 'owner')
    but org admins use member.role === 'orgadmin' — POST likely 401 for real
    admins; (2) success: string responses double-wrap via ResponseTransformInterceptor;
    (3) getTerms uses unbounded member join (multi-org leak) vs requireOrganizationId
    on mutations; (4) updateTerm sets updateData.id = termId and breaks empty-body
    guard; (5) duplicate UpdateTermDto in update-term.dto.ts (unused); (6) no
    runWithDbContext on GET; (7) no LoggingInterceptor; (8) create returns data: null
    (no new term id). Database design for academic_term is strong (unique year+slot,
    partial unique ACTIVE, CHECK term_start < term_end).

2) EXCEPTION FILTERS — General use and improvements for this route
--------------------------------------------------------------------------------

How they work (this project)
  • AllExceptionsFilter global; runWithDbContext maps PG errors on mutations.

Term-specific usage today
  • createTerm / updateTerm use runWithDbContext('term', ...). ✅
  • getTerms has no runWithDbContext — DB errors → generic 500.
  • validateTermDates → BadRequestException before DB.
  • NotFoundException when PATCH updates zero rows.

Mapped errors (postgres-error.mapper.ts)
  • 23505 + 'term' → 409 "A term with this academic year and term slot already exists"
  • 23503 — no term-specific branch (term delete not exposed)

Improvements
  A) Wrap getTerms in runWithDbContext('term', ...).
     FIX: getTerms wrapped in runWithDbContext('term', 'Failed to fetch terms', ...). ✅
  B) Standardise success: true (boolean) — fix double-wrap (§5).
     FIX: getTerms, createTerm, and updateTerm return { success: true, data }. ✅
  C) Map 23503 if DELETE term is added later (blocked by assignments/enrollments).
     FIX: postgres-error.mapper case 'term' for 23503. ✅
  D) TermsExceptionFilter — optional, low priority.

--------------------------------------------------------------------------------

Current usage

  • Global ValidationPipe with whitelist, transform, 422.

Gaps and recommendations

  A) Duplicate UpdateTermDto (medium)
     dto/update-term.dto.ts duplicates term.dto.ts UpdateTermDto with an extra
     @IsUUID() id field — controller imports from term.dto.ts only. Delete orphan
     file or consolidate.
     FIX: Deleted file ✅

  B) @MaxLength on academicYear (medium)
     Schema varchar(16). DTO has @MinLength(1) but no @MaxLength(16).
     FIX: Added maxlength 16 ✅

  C) PATCH partial date validation (medium)
     validateTermDates only sees fields in the PATCH body. Updating termStart alone
     does not compare against existing termEnd in DB (and vice versa). Options:
     load current row in service or reject partial date-only PATCH without both.
     FIX: To be reviewed... 📌

  D) @IsInt on termDays — OK with transform. ✅

  E) status enum — @IsIn matches schema enum. ✅


4) GUARDS — General use and current / improved usage
--------------------------------------------------------------------------------

Guard execution order
  1. Global AuthGuard
  2. OrgAdminGuard on TermController
  3. Handler

Current state — adequate for org-admin term management ✅

  A) createTerm vs requireOwnerOrganizationId (high — bug)
     Controller allows orgadmin (session user.role). Service create uses
     requireOwnerOrganizationId which queries member.role === 'owner'. Schema and
     Better Auth use member.role === 'orgadmin'. POST /terms likely fails with
     401 for legitimate school admins.

     Fix: use requireOrganizationId (match updateTerm) OR change helper to
     accept orgadmin owner role. ✅

  B) TermStatusGuard (medium)
     Should ARCHIVED terms reject further PATCH? Should only DRAFT → ACTIVE be
     allowed from UI? Enforce in service if product requires.
     FIX: Yes, business logic ✅

  C) requireActive on downstream modules — classes/assessment use
     requireTermInOrganization; term module itself does not require active for
     setup edits — OK for term setup page.

10) DB DESIGN ISSUES (given business logic)
--------------------------------------------------------------------------------
  • Term identity = (organizationId, academicYear, term) — matches API immutability. ✅
  • One ACTIVE per org — partial unique index + service demotion. ✅
  • CASCADE on gradingEntry / assessmentStructure when term deleted — but term
    DELETE not exposed; RESTRICT from assignments/enrollments blocks delete. ✅
  • templateSchema / templateUrl on term — pro feature; not in API yet. 📌
  • Status workflow DRAFT/ACTIVE/ARCHIVED — score locking implied; enforce in
    record/assessment modules when ARCHIVED. 📌


11) DB / SCHEMA OPTIMISATION (schema.ts — academic_term)
--------------------------------------------------------------------------------

academic_term
  • UNIQUE (organizationId, academicYear, term) — matches 409 mapper. ✅
  • partial UNIQUE (organizationId) WHERE status = 'ACTIVE' — belt + suspenders. ✅
  • CHECK term_start < term_end — DB enforces; service validates too. ✅
  • INDEX (organizationId), (organizationId, status) — good for list + active lookup.
  • FK organizationId ON DELETE RESTRICT — OK.
  • ON DELETE CASCADE to grading_entry, assessment_structure.
  • ON DELETE RESTRICT from subject_class_assignment, student_subject_enrollment.

Cascade summary
  • Delete term with class assignments → BLOCKED (23503).
  • Delete org → BLOCKED by RESTRICT chain.

Optional hardening
  • CHECK academic_year length / trim.
  • Index INCLUDE (academic_year, term, status) for list hot path at scale.
