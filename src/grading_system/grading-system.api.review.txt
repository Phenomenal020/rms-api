EXECUTIVE SUMMARY
--------------------------------------------------------------------------------
The grading-system module stores per-term grade bands (label, min/max score,
remark) via GET (by termId) and POST (full replace: DELETE all + INSERT all).
It uses OrgAdminGuard, requireTermInOrganization, rich validateGradingEntries
(contiguous 0–100 coverage, no overlaps), and runWithDbContext on save. The
full-replace strategy is justified: nothing references gradingEntry.id by FK.

Main gaps: (1) success: string + ResponseTransform double-wrap; (2) GET lacks
runWithDbContext; (3) POST returns 200 not 201 (minor REST semantics); (4) no
LoggingInterceptor; (5) @ArrayMaxSize missing; (6) allow empty entries on save?
(validation requires ≥1); (7) remark @MaxLength vs schema 256. Database design is
solid: unique grade per term, score range CHECKs, CASCADE with term.

10) DB DESIGN ISSUES
--------------------------------------------------------------------------------
  • Grading bands are term-scoped — correct (may differ per term/year). ✅
  • No FK from scores to grading_entry — letter grades computed in app from
    numeric score + bands; changing bands does not orphan score rows. ✅
  • Full replace safe — documented in service. ✅
  • remark optional — nullable column. ✅


11) DB / SCHEMA OPTIMISATION
--------------------------------------------------------------------------------

grading_entry
  • UNIQUE (academicTermId, grade) — matches validation. ✅
  • CHECK min_score <= max_score; 0 <= scores <= 100. ✅
  • INDEX academicTermId, organizationId. ✅
  • FK academicTermId ON DELETE CASCADE — bands removed with term.
  • FK organizationId ON DELETE RESTRICT.

Cascade summary
  • Delete term → CASCADE grading entries.
  • Delete org → RESTRICT via organizationId.

Optional
  • No downstream RESTRICT — full replace is correct.
  • Consider storing bands sorted by minScore in API response for client convenience.
